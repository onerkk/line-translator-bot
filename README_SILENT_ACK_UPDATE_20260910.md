# 通知按鈕只記錄後台：2026-09-10.3

本更新接續 `line-translator-ack-fix-20260910.zip`，只收錄本次修改的檔案。請依壓縮檔中的相對路徑覆蓋已套用前兩次更新的專案，再重新部署並重啟所有服務程序。

## 修正後的行為

| 操作 | 後台 | LINE 群組 |
| --- | --- | --- |
| 名單內的人按「了解」 | 記錄已了解，移出未回覆名單 | 不回話、不重送卡片、不重新標記 |
| 名單內的人按「需說明」 | 記錄需要說明，移出未回覆名單 | 不回話、不重送卡片 |
| 按原「查看回覆」按鈕 | 僅記錄首次查閱，重複點擊不覆寫；查閱不算回覆 | 不再發送狀態卡；新按鈕標示「記錄查閱」 |
| 名單內且有工廠管理權限的人按「停止提醒」 | 停止該通知，保留原有停止紀錄 | 不發停止提示 |
| 不在本通知名單的人點擊上述按鈕 | 不新增成員、回覆、查閱或停止紀錄 | 不回應 |
| 後台設定的提醒時間到達 | 重新核對未回覆名單 | 只個別 @ 仍未回覆的人 |
| 未回覆人數降為 0 | 自動結束提醒 | 不發完成卡片，也不再提醒 |

發起人本來就不在待回覆名單，因此點擊通知按鈕也不會留下回覆或操作紀錄。停止通知可使用「工廠工具 → 作業確認紀錄」的後台管理按鈕；既有管理權限檢查保留。

舊卡片的按鈕同樣套用新的後端規則，不會為更新外觀而重發舊卡片。通知以外的翻譯樣式、分享、工廠工具、表單與管理操作保留。

## 實際找到的問題

1. 原程式只讓成功的「了解／需說明」保持安靜。「查看回覆」仍會呼叫發訊函式，重送包含原文、譯文及回覆統計的整張卡；停止、過期、關閉確認、儲存失敗等分支也有群組提示。現在通知控制事件有共同的禁止發訊邊界，正常與異常路徑都不呼叫群組回覆或推播備援。
2. 原本先記錄點擊者的成員資料，再判斷是否為通知對象；全群模式也允許未列入通知的人留下回覆。現在先依通知保存的 LINE 身分名單判斷，再寫入，原子更新時也再次檢查；不透過點擊擴大名單。
3. 舊通知資料遺失、從有效上下文補建時，原本會先寫入「等待首次發送」，之後才記錄回覆。已用測試重現：若提醒程序恰好在兩次寫入之間執行，就會再次送出確認卡。現在補建直接保存「原卡已由有效點擊證明收到」，下一次喚醒設在提醒間隔之後，消除這個立即重送空窗。
4. 回覆記錄使用保存的通知姓名與已知姓名，不再等候 LINE 個人資料 API，降低按鈕處理的外部依賴。

這些是從提供的程式及本機重現確認的缺口。未取得當時正式伺服器的日誌或部署版本，因此不能只憑截圖斷言當時按「了解」一定走了其中哪個分支。

## 提醒與儲存

- 一般回覆不提前提醒、不重設其他人的提醒時間；後台原有間隔、持續提醒、關閉群組與停止單筆通知的設定保留。
- 提醒前仍核對最新回覆與離群紀錄，名單不完整也不改用 `@All`。保留原有分批及穩定重試識別碼。
- 儲存失敗時不偽造成功回覆，也不向群組發錯誤卡；保留錯誤日誌、非成功 webhook 回應及原有佇列恢復機制。
- LINE webhook 簽章驗證、事件去重及技術錯誤日誌保留；「不記錄名單外點擊」指不新增上述業務資料。

## 官方依據（2026-09-10 實際查閱）

- [LINE Postback action](https://developers.line.biz/en/docs/messaging-api/actions/#postback-action)：按鈕可只將事件送到伺服器。新通知按鈕不帶聊天顯示文字，後端不呼叫發訊 API。
- [LINE 接收 webhook](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)：保留簽章驗證及重送事件處理；收到 postback 不代表必須回傳聊天訊息。
- [LINE API 重試](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)：保留原有相同推播內容使用相同 `X-Line-Retry-Key` 的機制；LINE 已接受的請求不能改內容後沿用相同識別碼。
