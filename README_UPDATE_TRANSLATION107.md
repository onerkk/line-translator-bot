## 本次修正

1. **數字與欄位綁定。** 原檢查會接受把「實重 682、TAG 677」翻成實重 677、TAG 682，也會接受原文沒有的 kg。本次由原文建立「欄位 → 數值 → 單位」關係，第一輪提示、提供者回應檢查、最終傳送與快取驗證共用同一份規則。支援中印雙向的實重、TAG 登錄值、淨重與毛重；保留未註明的單位，不自行推定公斤。
2. **帳務語意與提問狀態。** 依既有廠內帳務規則，把「入非本月」解釋為資料錄入非本月分類；不推定為上個月，也不推定實際進倉月份。明確寫入庫、儲區等實體地點時，不套用這項分類判斷。「TAG 尚未更換／已更換」及提問語氣分別檢查。這是本專案的廠內語意設定，不是所有中文對話通用的詞義。
3. **完整欄位直接翻譯。** 像「實重682 TAG入677」可從明確欄位直接產生「Berat aktual 682; Angka pada TAG tercatat 677.」，省去一次 AI 生成。必須完整解析整句才能使用；附加問題、條件或作業要求會走原有模型流程。仍通過原有品質檢查，歷史對話也不能補入當句沒有的數值、單位。
4. **防止待翻譯訊息卡住。** 修正訊息已持久保存後，工作器啟動時若暫時無法讀取佇列，可能沒有工作器繼續處理的缺口。現在會啟動恢復工作器，不必等下一則訊息才恢復。保留既有補送、租約、防重複、重啟續作及 LINE 失敗重試。
5. **減少資料庫往返。** 佇列在同一條連線上檢查資料庫版本並完成操作；原有 SQLite WAL、FULL 落盤、交易與租約檢查保留。量測中的公告傳送，佇列連線由 48 次減至 24 次。
6. **舊快取重新驗證。** 新語意模組納入翻譯資產版本指紋；快取命中仍驗證欄位關係。錯譯不得因先前曾被保存就再次被採用。模型選擇與既有高風險審查設定沿用。

此環境沒有正式 AI、LINE 金鑰或生產日誌，尚未量測真實模型的翻譯正確率及上線後秒數，也無法認定每張漏譯截圖都由同一原因造成。上述測試證明本次可重現缺口已修正，並非所有未來工廠用語的零錯誤保證。外部 AI 或 LINE 中斷期間，無法完整產生／送達的訊息會保留待送，服務恢復後補送。

## 方法依據

- 官方建議減少不必要的串行請求，並對明確可由程式完成的工作採用傳統處理。本次將完整欄位訊息本機化，保留其他訊息的模型與品質檢查。[OpenAI 延遲最佳化](https://developers.openai.com/api/docs/guides/latency-optimization)
- 專業術語及歧義詞需要領域定義。本次把廠內帳務分類與欄位角色寫成共用語意契約；沒有新增 Google 翻譯服務依賴。[Google Cloud 術語表](https://docs.cloud.google.com/translate/docs/advanced/glossary)
- 研究指出，文件翻譯表現不能直接證明模型正確使用上下文。因此本次明確原文數值優先，並加入上下文污染反例。[Context-Aware or Context-Insensitive?](https://aclanthology.org/2025.mtsummit-1.10/)
- LINE 建議支援的推送 API 從首次請求即使用重試鍵，暫時錯誤採退避重試。此包保留既有傳送身分與防重複流程。[LINE API 重試](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)
