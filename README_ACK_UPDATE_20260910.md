**為何會出現截圖的錯誤**

截圖中的「通知尚未確認建立成功」原本共用於儲存錯誤及翻譯失敗，不能僅憑這句話判定是哪一家服務故障。本次沒有正式環境日誌，不能宣稱已查到當時的供應商錯誤碼；但已在原程式重現並修正以下缺陷：

1. `/確認` 的翻譯分支清空 LINE 原生點名資料。`@budi santoso 山多` 等完整姓名可能被拆開，影響翻譯及語言判斷。
2. 姓名代碼使用逐一字串替換：`MENTION_1` 會誤中 `__MENTION_10__` 至 `__MENTION_19__`，造成代碼殘片、缺名及錯誤修復。現在完整比對代碼，一次還原；短姓名也不再被當成另一個長姓名中的額外出現次數。
3. 截圖末尾的普通文字 `@測試新指令` 被文字姓名規則保護，正文標題可能沒有翻譯。現在先分離開頭真正點名的收件人，姓名原樣保留，正文完整交給原有翻譯與品質檢查。
4. 原程式先翻譯、後保存通知。翻譯失敗時沒有持久待辦，直接回報錯誤；現在先保存原文、原生點名、收件人範圍與提醒設定，再翻譯及製作確認卡。
5. 主儲存服務在首次寫入前中斷時，同步 webhook 原本沒有本機恢復副本。現在使用原有 webhook 工作佇列保存已驗證簽章的原始事件，讓服務恢復後自動續做，同時保留 LINE 補送資格。
6. 原有數值檢查未涵蓋小時、分鐘及秒數，已重現把 `8小時` 翻成 `9 jam` 仍被送出的問題。現在共用品質檢查比較時間數值與單位，包含完整數字、常見文字數字及等值時間單位；錯誤時間會進入原有供應商容錯及待辦重試。無法辨識的文字數字不推測為另一個數值。

**更新後的行為**

- 完整譯文通過檢查才送出確認卡。翻譯未完成時保留待辦；不把錯誤訊息當成完成通知。
- 翻譯、儲存、LINE 傳送分別記錄失敗階段。後台顯示準備／翻譯重試狀態及下次處理時間。
- 已保存的譯文及 LINE 請求在傳送重試時沿用；同一請求沿用同一個 UUID 重試識別碼。
- 重複 webhook、程序重啟及同時處理不會覆蓋已完成的確認內容。過期的工作租約失效後可重新接手。
- 翻譯恢復使用獨立、有限數量的工作執行緒，避免慢速翻譯直接卡住已到期的提醒。
- 截圖設定 `480` 分鐘維持為 8 小時，從確認卡被 LINE 接受後開始計時；只追蹤指令中真正點名的成員，排除發起人、機器人、離群者與已回覆者。全部已回覆後停止。
- 既有停止提醒、收回／修改原文及群組關閉設定仍生效。準備中的通知不能提前記錄「已確認」。

**實際查閱的官方技術文件**

- [LINE：接收 webhook](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)：先驗證簽章；事件可重複且順序可能改變；補送需開啟並回傳非 2xx。補送本身不是可靠送達保證，且沒有事後重新取得文字內容的 API。因此保留原文、去重及持久待辦都必要。
- [LINE：失敗 API 重試](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)：支援的 push 請求從第一次就帶重試識別碼；重試不能更改內容及收件人；409 搭配已接受識別碼表示先前已被接受。Reply API 不支援這個重試標頭。
- [LINE：文字長度](https://developers.line.biz/en/docs/messaging-api/text-character-count/)：以 UTF-16 code units 計數，涉及 emoji 與點名位置；測試使用 SDK webhook 物件及 UTF-16 原生點名資料。
- [LINE：訊息型別](https://developers.line.biz/en/docs/messaging-api/message-types/)：textV2 使用 substitution 表達真正點名。確認卡中的姓名文字與發送點名的 userId 分開處理。
- [Render：免費服務限制](https://render.com/docs/free)：免費 Web Service 閒置 15 分鐘會休眠，喚醒約 1 分鐘；休眠、重啟或部署會遺失本機檔案，且不能掛載持久磁碟。

若正式環境仍使用 Render 免費休眠服務，程式更新無法讓休眠中的程序準時執行 8 小時提醒。正式排程需要持續運行的服務與持久儲存；LINE Developers Console 的 Webhook redelivery 也應保持開啟。此包未修改服務方案或控制台設定。
